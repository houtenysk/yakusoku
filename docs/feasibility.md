# 友人間「約束（契約）」アプリ 実現可能性の整理

## 0. 想定ユースケース

- A（実行する側）と B（確認する側）が「毎週の宿題を出す。未提出、または赤点なら A が 1,000 円を飲み会プールに入れる」と取り決める
- A は宿題（の写真など）を提出し、B は答えを見て採点する
- 未提出・赤点のときは罰金が発生し、共通プールに積み立てる
- プールは飲み会などで使う。最後にどこかのタイミングで清算する
- できれば、罰金が発生した時点で PayPay の送金リンクなどを使ってすぐ払えるようにしたい

## 1. 結論サマリ

| 区分 | 内容 |
|---|---|
| ✅ 素直に作れる | 約束の作成と相手の同意、期限管理と通知、提出（写真など）、B による採点と判定、罰金の発生記録（台帳）、プール残高の表示、精算額の計算、定期的な更新 |
| ⚠️ 工夫すれば作れる（手作業が残る） | PayPay での支払い（アプリは「支払ってください」と案内するだけで、送金はユーザーが PayPay アプリで行う）、支払い済みの確認（払った側の自己申告と、受け取った側の承認）、不正提出の抑止、AI による採点補助 |
| ❌ 設計上難しい／避けるべき | アプリが自動で引き落とす・送金する、アプリ運営者がお金を預かって共通プールを持つ、PayPay 上の「共同財布」、罰金を払わない人への強制力、双方がお金を賭ける形 |

**最大の分かれ目は「アプリがお金そのものに触るか」です。**
アプリは記録（台帳）と催促に徹し、実際のお金の移動は PayPay など既存サービスでユーザー自身が行う形にすると、技術・法律・審査のリスクがまとめて下がります。

## 2. 機能別の可否

### 2.1 約束の作成と合意 — ✅
- 中身：誰が・何を・いつまでに・どう判定するか（提出の有無、点数の閾値）・違反時はいくら・どこへ払うか・何回繰り返すか
- 相手を招待リンク（LINE で共有できる Universal Link）で呼び、相手が「同意」した時点で有効にする。双方が同意したことと日時を記録しておくと、後で揉めたときの根拠になる
- 「更新」は、週ごとなどの繰り返しで自動的に次回の課題を作るか、期間が終わるたびに双方で再同意する形で実装できる

### 2.2 提出 — ✅（不正対策には限界あり）
- 写真やファイルを上傳し、サーバー側の時刻を提出時刻として記録する。期限を過ぎたら自動的に「未提出」と判定する
- 撮影はアプリ内カメラに限定し、ライブラリからの選択を禁止するといった抑止はできる。ただし「他人に解いてもらう」「答えを写す」は技術的に防げない。最終的には B が見て判断するしかない

### 2.3 採点・判定 — ✅（手動）／⚠️（自動）
- B が提出物を見て点数を入力し、合否を確定する。これはそのまま作れる
- 答えの画像と提出物を AI（OCR と LLM）で照合して採点案を出すこともできる。ただし誤判定がありうるので、あくまで補助にして B が確定する
- 異議申し立てを用意しておく（A が異議を出す → 再判定、またはグループの第三者が判定する）。罰金を受け取る側が判定者も兼ねるため、利益相反が起きやすい点に注意

### 2.4 罰金の発生とプールの台帳 — ✅
- 判定が確定したら、台帳に「A → プール 1,000 円（未払い）」と記録する
- 状態は「未払い → 支払い報告済み → 受領確認済み」の 3 段階で管理する
- プールの残高、各自がいくら入れたか、いくら使ったかはアプリで表示できる

### 2.5 PayPay での支払い — ⚠️（ユーザーの手作業が必須）
- **PayPay の個人間送金を外部アプリから実行・自動化する公開 API はない**（PayPay for Developers は加盟店が支払いを受けるためのもの）
- PayPay アプリ側の機能として、電話番号・PayPay ID・QR コード・受け取りリンクを使った個人間送金がある。ただし、受け取りリンクは PayPay アプリの中で本人が作る必要があり、こちらのアプリから金額入りで生成することはできない
- 現実的な流れは次のとおり
  1. 罰金が発生すると、A にプッシュ通知「プール（幹事 B）へ 1,000 円送ってください」が届く
  2. A は PayPay を開き、B の PayPay ID や QR を使って送るか、受け取りリンクを作って B に共有する
  3. A がアプリで「支払った」を押し、B が「受け取った」を押して完了する
- 「その場で払う」は通知と導線で近い体験になる。ただし本当の即時・自動化はできない

### 2.6 共通プール — ⚠️（「幹事の口座＋アプリの台帳」で代用）
- PayPay には友人同士の共同口座や共同財布の仕組みがない
- 代わりの方法は 2 つ
  - **A 案：幹事方式**。プールの管理者（例：B）を決め、その人の PayPay 残高に集める。アプリの台帳で「このうちプール分はいくら」を管理する
  - **B 案：送らない方式**。罰金はアプリの台帳にツケとして記録するだけで、飲み会のときにまとめて差し引き精算する。お金の移動回数が最も少なく、手間も揉め事も少ない
- MVP では B 案を基本にし、「すぐ払いたい人」は A 案でも払えるようにするのがおすすめ

### 2.7 精算 — ✅
- 飲み会の会計、プール残高、各自の未払い罰金を合算し、送金回数が最小になる精算案を出す（Splitwise や Walica と同じ考え方）
- 送金そのものは 2.5 と同じく、ユーザーが手動で行う

### 2.8 払わない人への強制 — ❌
- 友人間の取り決めも法的には契約になりうる。ただし少額の罰金を実際に強制する手段はない。現実的にはリマインドとグループ内での見える化（未払い表示）という社会的な圧力に頼ることになる
- これはこの手のアプリに共通する限界で、設計で無理に解決しようとしないほうがよい

## 3. 設計上の大きな壁（法律・プラットフォーム）

> ここでの法律の話は一般論です。公開・収益化する前に、弁護士（フィンテックや資金決済に詳しい人）に確認してください。

### 3.1 アプリがお金を預かると「資金移動業」の問題が出る
- 運営者がユーザーからお金を受け取り、プールとして保管して後で誰かに払い出す。これは為替取引にあたる可能性が高く、資金決済法上の資金移動業の登録が必要になりうる（個人開発ではまず無理）
- PayPay の加盟店 API で運営者の口座に集金し、そこから分配する形も同じ問題になる。割り勘アプリのような「収納代行」型の集金も、規制の対象として扱う方向で議論が進んでいる
- **→ アプリはお金に触らず、台帳と案内だけにするのが安全**

### 3.2 賭博罪とみなされるリスク
- 「A が自分の課題を守れなかったら一方的に違約金を払う」というコミットメント型なら、典型的な賭博とは性質が違うと考えられる
- 一方で、「合格したら B が A に払い、不合格なら A が B に払う」といった**双方がお金を賭ける形**や、運や偶然が結果を左右する取り決めにすると、賭博に近づく
- **→ 罰金を払うのは実行者だけにし、金額に上限を設け、行き先は「飲み会プール（本人も使う）」にする、という設計が無難**

### 3.3 未成年の利用
- 「宿題」なら利用者が未成年である可能性が高い。未成年が法定代理人の同意なしに結んだ契約は取り消せる。PayPay 側にも年齢や本人確認による機能の制限がある
- **→ 18 歳以上限定にするか、未成年向けにはお金を伴わない「ポイント」や「罰ゲーム」モードを用意する**

### 3.4 App Store 審査
- 実際のお金で賭ける系のアプリは厳しく審査される。コミットメント系のアプリ自体は前例がある
- アプリ内で金銭のやり取りを完結させず、案内と記録に徹する設計なら説明しやすい
- 説明文では「賭け」や「ベット」という表現を避け、「約束」「目標達成」「違約金」として打ち出す

## 4. 推奨アーキテクチャ（MVP）

「**お金に触らない約束と台帳のアプリ**」とする。

- iOS：SwiftUI
- バックエンド：Firebase（Sign in with Apple による認証、Firestore、提出画像用の Storage、Cloud Functions による期限判定、FCM と APNs による通知）
- 招待：Universal Link を LINE などで共有する
- 支払い：PayPay は「開く導線」と送り先（PayPay ID や QR 画像）の表示だけにする。完了は「支払い報告」と「受領確認」の 2 段階で管理する
- 別の選択肢：友人間での利用が中心なら、LINE ミニアプリ（LIFF）のほうが配布と招待が楽な可能性がある。ストア審査も不要になる

### データモデル（概略）
- `Group`：メンバー、プール管理者
- `Contract`：実行者、確認者、条件（期限・閾値）、違約金額、繰り返し設定、双方の同意日時、状態
- `TaskInstance`：各回の課題（期限、状態）
- `Submission`：提出物、サーバー時刻
- `Judgment`：点数、合否、コメント、異議の有無
- `LedgerEntry`：罰金、プールからの支出、精算（金額、支払う人と受け取る人、状態：未払い／報告済み／確認済み）

## 5. MVP の範囲案

1. 2 人用の約束の作成、招待、同意
2. 繰り返しの課題と期限通知
3. 写真の提出と、確認者による採点・判定
4. 罰金の台帳とプール残高の表示
5. 「支払いました」「受け取りました」の 2 段階確認と PayPay への導線
6. 飲み会での精算計算

後回しにするもの：AI 採点、3 人以上のグループ、異議申し立てで第三者が判定する仕組み、未成年向けモード
